# 工作移交（人员变更）设计方案

## 一、项目概述

### 背景

审计项目或整改项目的工作启动后，常出现项目成员变更、移除的情况（离职、轮岗、工作调整等）。被变更成员名下往往还挂着进行中的审计事项、未完结的审计文书以及在途的审批数据（审核中的决定、待反馈的移送等）。若直接移除成员，这些工作会失去归属、审批流程中断。

### 目标

参照钉钉、飞书的工作交接逻辑，在**项目内**提供一套"工作移交"机制：项目组长 / 主审在变更或移除某成员前，先把该成员名下的审计事项、审计文书、审批数据**分项指派**给同项目的其他成员，提交后**即时生效**，在途审批自动转交接收人继续处理，全程留痕可追溯。

### 核心价值

- 人员变更不丢工作、不断流程
- 一个界面看全"谁的什么工作交给谁"，分项分人灵活指派
- 在途审批无缝转交，接收人直接接力
- 移交全程留痕，满足审计追溯要求

### 设计基线（需求确认结论）

| 维度     | 结论                                                  |
| -------- | ----------------------------------------------------- |
| 发起方   | 项目组长 / 主审（项目内工作调配，非全局离职交接）     |
| 范围     | 单个审计 / 整改项目内部，入口在项目详情的「人员管理」 |
| 颗粒度   | 分项移交，不同工作项可指派给不同接收人                |
| 生效机制 | 即时生效（提交即转移，无需接收人确认）                |
| 在途审批 | 审核中的决定、待反馈的移送等自动转交接收人继续处理    |

## 二、功能范围与核心模块

```
工作移交（项目内）
├── 人员管理入口      项目详情 → 项目成员 → 「人员管理」弹窗
│   ├── 成员行新增「变更 / 移除」操作（替代直接增删）
│   ├── 变更：发起工作移交向导
│   └── 移除：先校验名下工作，有工作必须先移交再移除
├── 移交向导          选移出成员 → 分类清单分项指派 → 汇总确认
│   ├── 审计事项移交   AuditItem.assignedMembers 的替换
│   ├── 审计文书移交   Document 归属人的转移
│   └── 审批数据移交   在途的审计决定 / 审计移送 / 待办，转交接收人继续处理
├── 人员变更记录      可追溯：谁、何时、把什么、交给了谁、原因
└── 通知              接收人收到「工作移交通知」
```

核心模块：

1. **人员管理弹窗改造**：项目成员各角色行（组长 / 组员 / 审计可见角色 / 迎审可见角色 / 单位默认收件人）右侧增加操作列，提供「变更」「移除」，不再直接增删人员
2. **移交发起**：组长 / 主审对某成员发起，校验发起人权限
3. **工作归集**：按移出成员聚合其在本项目的事项、文书、审批三类工作
4. **分项指派**：每条工作项可独立选择接收人（接收人须为同项目成员）
5. **即时生效与转交**：提交后立即改写归属；在途审批单据的当前处理人改派给接收人
6. **记录与通知**：写人员变更 / 移交记录，向接收人推送通知

## 三、界面与交互设计

### 1. 人员管理弹窗（改造）

入口：项目详情顶部「项目成员」按钮 → 弹出「人员管理」弹窗。

改造点：原弹窗每个角色行直接用「选择」增删人员；现在每个成员标签右侧增加**操作列**，提供「变更」「移除」两个操作，并在弹窗右上角增加「人员变更记录」入口。

```
┌─ 人员管理 ───────────────────────────────────────────────┐
│ │ 项目成员                                  人员变更记录 → │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 组长   │ 王-W（总部审计部）        │ [变更] [移除]      │ │
│ │ 组员   │ 白-J（总部审计部）        │ [变更] [移除]      │ │
│ │ 审计可见角色 │ —                   │ [选择]            │ │
│ │ 迎审可见角色 │ —                   │ [选择]            │ │
│ ├──────────────────────────────────────────────────────┤ │
│ │ 单位默认收件人                                          │ │
│ │ ZY股份 │ 单位经办人员（ZY股份）   │ [变更] [移除]      │ │
│ └──────────────────────────────────────────────────────┘ │
│                                          [取消]  [保存]   │
└──────────────────────────────────────────────────────────┘
```

交互规则：

- 「变更」：打开工作移交向导，把该成员名下工作交给接收人后，再用新成员替换
- 「移除」：先检查该成员名下是否有未完结工作，**有则提示必须先移交**，无则确认后移除
- 可见角色等无工作归属的纯权限位，仍保留「选择」直接增删

### 2. 工作移交向导（抽屉，单页三 Tab）

```
┌─ 工作移交 ──────────────────────────────────────┐
│ 移出成员：白-J（组员）          移交原因：[______] │
│ ┌─────────────────────────────────────────────┐ │
│ │ 审计事项(5) │ 审计文书(8) │ 审批数据(3)        │ │ ← Tab
│ ├─────────────────────────────────────────────┤ │
│ │ ☑ 事项1  采购合规检查   状态:进行中           │ │
│ │     接收人 ▸ [李四 ▾]                          │ │
│ │ ☑ 事项2  固定资产盘点   状态:待开始           │ │
│ │     接收人 ▸ [王五 ▾]                          │ │
│ │ [批量指派接收人 ▾]  [全选]                     │ │
│ └─────────────────────────────────────────────┘ │
│ 已选 12 项 → 待提交                  [取消][下一步] │
└──────────────────────────────────────────────────┘
```

确认步骤：按"接收人"维度汇总——李四将接收 X 个事项、Y 份文书、Z 条审批，发起人最后核对"谁接了什么"再提交。

关键交互规则：

- 接收人下拉只列同项目其他在职成员，排除移出成员本人
- 支持「批量指派」：勾选多项后一次性指定同一接收人
- 审批数据项标注当前流转状态（审核中 / 待下达 / 待反馈），提示"将转交接收人继续处理"
- 已完成、已归档的工作项默认折叠，可展开仅改历史归属人

## 四、数据结构与流向

### 1. 工作移交记录实体 `WorkTransferRecord`

```typescript
// 工作移交记录（一次移交可含多条明细，明细可指向不同接收人）
interface WorkTransferRecord {
  id: number
  projectId: number // 所属项目
  projectName: string
  fromMemberId: number // 移出成员
  fromMemberName: string
  reason: string // 移交原因
  operatorId: number // 发起人（组长 / 主审）
  operatorName: string
  transferTime: string
  items: WorkTransferItem[] // 移交明细
  itemCount: number // 明细总数（事项 + 文书 + 审批）
}

// 单条移交明细：一个工作项 → 一个接收人
interface WorkTransferItem {
  id: number
  category: 'item' | 'document' | 'approval' // 事项 / 文书 / 审批
  refId: number // 指向 AuditItem / Document / 审批单据的 id
  refName: string // 工作项名称（冗余，便于记录展示）
  refStatus?: string // 移交时该工作项的状态快照
  toMemberId: number // 接收人
  toMemberName: string
}
```

### 2. 三类工作项的归属改写规则

| 类别 | 来源实体 | 归属字段 | 移交动作 |
| --- | --- | --- | --- |
| 审计事项 | `AuditItem.assignedMembers` | 该数组中的成员 | 将移出成员从 `assignedMembers` 移除，加入接收人（去重） |
| 审计文书 | `Document`（按人分组） | 文书归属人 | 归属人从移出成员改为接收人 |
| 审批数据 | `AuditDecision` / `AuditTransfer` / 待办 | 当前处理人 / `issuedBy` / 反馈处理人 | 在途单据的当前处理人改派为接收人 |

### 3. 数据流向

```
组长 / 主审在「人员管理」点击「变更」或「移除」
   │
   ▼
按 projectId + fromMemberId 归集三类工作
   │  · 审计事项：assignedMembers 含该成员的
   │  · 审计文书：归属该成员的 Document
   │  · 审批数据：当前待该成员处理的在途单据
   ▼
逐项指派接收人（接收人 ∈ 同项目在职成员）
   │
   ▼
提交 → 即时生效：
   ├─ 写入 WorkTransferRecord + items
   ├─ 改写各实体归属字段
   ├─ 在途审批单据当前处理人改派 → 接收人待办出现该单据
   └─ 推送「工作移交通知」给各接收人
   ▼
人员变更记录 / 移交记录页可追溯查询
```

## 五、边界情况处理

| 场景 | 处理规则 |
| --- | --- |
| **发起人权限** | 仅本项目组长 / 主审可见「变更 / 移除」并发起；普通组员、查看人无权限 |
| **接收人范围** | 只能选同项目其他在职成员，排除移出成员本人；若接收人后续也要移除，需另起一次移交 |
| **移除有工作的成员** | 名下有未完结工作时，「移除」拦截并提示"该成员尚有工作未移交，请先完成工作移交"，引导先走变更流程 |
| **移出成员无工作** | 三类均为空时，「变更」可直接替换人员；提示"该成员在本项目暂无可移交的工作" |
| **未指派接收人** | 已勾选但未选接收人的工作项，提交时拦截并高亮提示 |
| **在途审批的处理人改派** | 审核中 / 待下达 / 待反馈的单据，当前节点处理人改为接收人；已流转过的历史审批记录保留原处理人，不篡改 |
| **已完成 / 已归档工作项** | 允许改归属人（用于责任延续），但状态、内容不变；归档项默认折叠，需手动展开勾选 |
| **同一工作项重复移交** | 以最后一次移交的归属为准；移交记录各自留痕，可见完整流转链 |
| **接收人已是事项成员** | 审计事项 `assignedMembers` 去重，避免重复加入 |
| **移交原因** | 必填，便于审计留痕（离职 / 轮岗 / 工作调整等） |
| **并发冲突** | 同一成员的工作正在被移交时，二次发起需基于最新归集结果，避免移交已转走的项 |
| **可见角色 / 收件人位** | 无工作归属的纯权限位，保留直接「选择」增删，不走移交流程 |
